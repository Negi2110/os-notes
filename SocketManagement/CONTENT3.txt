# Sockets, Connections and Queues — Complete Interview Study Notes

---

## Socket

### What is a Socket?

When a process listens on an IP/Port, the kernel produces a socket for it.

- Socket is a file (at least in Linux) — represented as a file descriptor (an integer)
- The process owns the socket
- Can be shared during fork — child process inherits parent's file descriptors including the socket
- The kernel manages all the underlying network buffers and state associated with the socket

Think of a socket as the kernel's representation of a network endpoint. Your application doesn't talk to the network directly — it talks to the socket, and the kernel handles everything below.

---

## SYN Queue and Accept Queue

### How queues are created

When a socket is created via the `listen()` system call, the kernel automatically creates two internal data structures alongside it:

```c
#include <sys/socket.h>
int listen(int sockfd, int backlog);
```

The `backlog` parameter controls the size of these structures.

### SYN Queue (Incomplete connections)

- Stores incoming SYN packets
- When a client sends a SYN, the kernel adds an entry to this queue and replies with SYN/ACK
- The entry stays in the SYN queue until the final ACK arrives from the client (completing the 3-way handshake)
- If the SYN queue is full (e.g. during a SYN flood attack), new SYNs are dropped
- This is the kernel's in-progress handshake holding area

### Accept Queue (Complete connections)

- Stores fully established connections (3-way handshake complete)
- When a connection moves here, it's ready for the application to pick up
- The application calls `accept()` to dequeue a connection and get a file descriptor for it
- If the application is slow to call `accept()` and this queue fills up, new connections are dropped even though the handshake completed successfully
- Size bounded by the `backlog` parameter

### Important detail

These are technically not queues but hash tables. The OS looks up connections by their 4-tuple (SrcIP, SrcPort, DstIP, DstPort) for fast O(1) dispatch. The term "queue" is used loosely.

## Connection, Receive and Send Queue

### What happens when accept() is called

```c
#include <sys/socket.h>
int accept(int sockfd, struct sockaddr * restrict addr, socklen_t * restrict addrlen);
```

- Completed connections sit in the accept queue
- When the backend process calls `accept()`, a connection is dequeued
- `accept()` returns a new file descriptor specifically for this connection (different from the listening socket fd)
- Two new kernel-managed queues are created for this connection:

### Send Queue (C Send Queue)

- Stores outgoing data that the application has written but TCP hasn't fully transmitted yet, or has transmitted but not yet received an ACK for
- Unacknowledged data must be retained in the send buffer because it may need to be retransmitted
- When the application calls `write()` or `send()`, data goes into this buffer first, then TCP picks it up and sends it

### Receive Queue (C Receive Queue)

- Stores incoming data that the kernel has received from the network but the application hasn't read yet
- When the application calls `read()` or `recv()`, it drains from this buffer
- The amount of free space in this buffer is what TCP advertises as the window size to the sender — this is how flow control works
- When this buffer fills up, the advertised window shrinks to zero, telling the sender to stop sending

## Connection Establishment — Step by Step (What Actually Happens in the Kernel)

### High level flow

1. Server listens on an address:port
2. Client connects
3. Kernel does the handshake, creating a connection
4. Backend process calls `accept()` to pick up the connection

### Detailed kernel-level flow

Step 1: Kernel creates a socket and two queues — S SYN Queue and S Accept Queue — when `listen()` is called.

Step 2: Client sends a SYN.

Step 3: Kernel adds an entry to the SYN queue, replies with SYN/ACK.

Step 4: Client replies with ACK.

Step 5: Kernel finishes the connection — removes the entry from the SYN queue.

Step 6: Kernel adds the fully established connection to the Accept queue.

Step 7: Backend process calls `accept()` — the connection is removed from the accept queue.

Step 8: A file descriptor (PID-level) is created for this connection. The application now has a handle to read/write data on this connection.

Step 9: Two new queues are created for this connection: C Send Queue and C Receive Queue.

### Diagram description

```
Client                    Kernel (Server Side)
  |                            |
  |------- SYN --------------->|  [SYN Queue: entry added]
  |<------ SYN/ACK ------------|
  |------- ACK --------------->|  [SYN Queue: entry removed]
                               |  [Accept Queue: connection added]
                          accept() called by backend
                               |  [Accept Queue: connection removed]
                               |  [File descriptor created for connection]
                               |  [C Send Queue + C Receive Queue created]
```

## Problems with Accepting Connections

Three common failure modes that prevent connections from being accepted properly:

### 1. Backend doesn't accept fast enough

- If the application is slow to call `accept()`, the accept queue fills up
- New connections coming in have nowhere to go and are dropped
- Symptom: clients see connection timeouts or refused connections even though the server is "up"
- Fix: faster accept loop, more worker threads/processes, non-blocking I/O with event loops (like Node.js does with libuv)

### 2. Clients who don't ACK (SYN flood)

- Attacker sends SYNs with spoofed source IPs
- Kernel adds entries to SYN queue and sends SYN/ACK
- Final ACK never arrives (spoofed host doesn't exist)
- SYN queue fills up — legitimate clients' SYNs get dropped
- Fix: SYN cookies — encode connection state in the SYN/ACK sequence number so no SYN queue entry is needed. When the real ACK arrives, the state is reconstructed from the sequence number.

### 3. Small backlog

- If `backlog` is set too small in `listen(sockfd, backlog)`, both queues are tiny
- Under burst traffic, queues fill instantly and connections are dropped
- Fix: tune the backlog value. Also tune kernel parameters: `net.core.somaxconn` (system-wide max backlog) and `net.ipv4.tcp_max_syn_backlog` (SYN queue size)

## Socket Sharding

### The problem

Normally, only one process can listen on an active IP/port pair. If you try to bind two processes to the same port, the second one fails.

### SO_REUSEPORT

- Linux socket option that overrides this restriction
- Allows two distinct sockets in different processes (or threads) to listen on the same IP/port pair
- The kernel load-balances incoming connections across all sockets sharing that port
- Each socket has its own SYN queue and accept queue

```c
int opt = 1;
setsockopt(sockfd, SOL_SOCKET, SO_REUSEPORT, &opt, sizeof(opt));
```

### Why this matters

- Traditional multi-process servers had one listening socket shared via fork — all workers compete to call `accept()` on the same socket (the "thundering herd" problem)
- With SO_REUSEPORT, each worker has its own socket and accept queue — no contention
- The kernel itself distributes connections, usually via a hash of the 4-tuple
- Used by Nginx, Node.js cluster module, and modern high-performance servers

---

## Summary

- Kernel manages all networking — your application only interacts via system calls (listen, accept, read, write, close)
- Socket represents a port/IP — it is a file descriptor, a kernel-managed object
- Each connected client gets its own connection — with its own send queue and receive queue
- All data structures (SYN queue, accept queue, send queue, receive queue) are kernel-managed — your application just calls the right syscalls and the kernel handles the rest

## Interview Questions — Sockets, Connections, and Queues

**Q: What is a socket and why is it called a file descriptor in Linux?**

A socket is the kernel's representation of a network communication endpoint. In Linux, the "everything is a file" philosophy means sockets are accessed through file descriptors — integers that index into the process's open file table. This lets you use the same read(), write(), close() system calls on sockets that you use on regular files. It also means sockets are inherited across fork() just like file descriptors.

---

**Q: Walk me through exactly what happens in the kernel when a TCP connection is established.**

1. Server calls `listen(sockfd, backlog)` — kernel creates a socket, a SYN queue, and an accept queue.
2. Client sends SYN — kernel adds an incomplete connection entry to the SYN queue and replies SYN/ACK.
3. Client sends ACK — kernel removes the entry from the SYN queue, marks the connection complete, and moves it to the accept queue.
4. Server calls `accept()` — kernel removes the connection from the accept queue, creates a new file descriptor for it, and allocates a send queue and receive queue for that connection.
5. Application can now read() and write() on the returned file descriptor.

---

**Q: What is the difference between the listening socket and the connected socket returned by accept()?**

The listening socket (created by socket() and listen()) is the server's doorbell — it only receives new connection requests. It has a SYN queue and accept queue but no per-connection send/receive buffers. The connected socket returned by accept() is a completely separate file descriptor dedicated to one specific client. It has its own send queue and receive queue and is used for all data exchange with that client. The server can have one listening socket and thousands of connected sockets simultaneously.

---

**Q: What happens if the accept queue is full?**

New fully-established connections (that completed the 3-way handshake) are dropped. The client will see a connection timeout or connection refused. This commonly happens when the application's accept loop is too slow — it can't drain the queue fast enough under high load. Solutions include increasing the backlog, using non-blocking I/O with an event loop, or multi-threading the accept loop.

---

**Q: What is a SYN flood and how do SYN cookies fix it?**

A SYN flood is a DoS attack where an attacker sends many SYN packets with spoofed source IPs. The server adds each to the SYN queue and sends SYN/ACK, but the final ACK never comes (the spoofed host doesn't exist). The SYN queue fills up, blocking all legitimate connections.

SYN cookies fix this by eliminating the SYN queue entry entirely. Instead of storing state, the server encodes all the necessary connection information (timestamp, MSS, etc.) into the SYN/ACK's initial sequence number using a cryptographic hash. When the legitimate client sends ACK, the sequence number carries that encoded state — the kernel can reconstruct the connection without ever having stored anything. Attackers whose SYNs go to non-existent hosts never send the ACK, so no state is wasted.

---

**Q: What is the receive queue and how does it implement flow control?**

The receive queue (receive buffer) stores data that the kernel received from the network but the application hasn't read yet via read()/recv(). The amount of free space in this buffer is advertised to the sender as the TCP window size in every outgoing ACK. When the application reads slowly and the buffer fills up, the advertised window shrinks. When it hits zero, the sender stops transmitting entirely. Once the application drains the buffer, the window opens again and the sender resumes. This end-to-end mechanism ensures the sender can never overwhelm the receiver regardless of network speed.

---

**Q: What is SO_REUSEPORT and when would you use it?**

SO_REUSEPORT is a Linux socket option that allows multiple processes or threads to bind to the exact same IP/port pair, each with their own independent socket. The kernel load-balances incoming connections across all bound sockets. You would use it to build high-performance multi-process servers where each worker has its own accept queue — eliminating the "thundering herd" problem where all workers wake up competing for a single connection on a shared socket. Nginx and Node.js cluster mode use this pattern.

---

**Q: What is the thundering herd problem in the context of sockets?**

When multiple processes/threads all block on accept() on the same listening socket, and a new connection arrives, the kernel wakes all of them up simultaneously. Only one can accept the connection — the rest go back to sleep. This mass wake-up and context switch storm is called the thundering herd. It wastes CPU on contention. Solutions: use SO_REUSEPORT so each worker has its own socket and is the only one woken for its connections, or use edge-triggered epoll with EPOLLEXCLUSIVE which wakes only one waiter.

---

**Q: Why does each connection get its own send queue and receive queue rather than sharing?**

Each connection is an independent stream of data between two specific endpoints. Mixing data from different connections in shared buffers would require complex locking and make it impossible to implement per-connection flow control — the window size must reflect the specific receiver's available buffer space. Independent queues also allow the kernel to retransmit data for one connection without affecting others, and let connections progress at their own rates without head-of-line blocking each other.

---

**Q: What kernel parameters would you tune to handle a high-connection-rate server?**

- `net.core.somaxconn` — system-wide maximum backlog for listen queues (default 128, should be 1024+ for production)
- `net.ipv4.tcp_max_syn_backlog` — maximum size of the SYN queue
- `net.ipv4.tcp_syncookies` — enable SYN cookies to protect against SYN floods
- `net.ipv4.ip_local_port_range` — range of ephemeral ports available for outgoing connections
- `net.core.netdev_max_backlog` — max packets queued on the NIC before the kernel processes them
- `ulimit -n` (or `nofile` in limits.conf) — max open file descriptors per process, since each connection is a file descriptor
